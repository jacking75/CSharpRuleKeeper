Analyzer를 연결하고, 팀 또는 개인의 코딩 스타일을 안전하게 설정하고, AI가 만든 코드까지 같은 기준으로 검사하는 과정을 한 번에 안내한다.

무엇을 해 주는 도구인가

CSharpRuleKeeper는 빌드 중에 코드 규칙을 알려 주는 Roslyn Analyzer다. IDE에서 미리 보이고 터미널 빌드에서도 다시 확인된다. 서식과 의미 검사를 분리하므로 무엇을 자동으로 고치고 무엇을 사람이 판단해야 하는지도 명확하다.

1. 규칙 작성.editorconfig에 들여쓰기·줄 길이·예외를 적는다.
2. 코드 작성IDE와 AI가 작성한 C# 코드를 같은 기준으로 본다.
3. 즉시 확인HBCS 진단, 빌드, 테스트로 결과를 확인한다.
💡
먼저 알아둘 한 가지
Analyzer는 코드를 마음대로 바꾸지 않는다. 문제의 위치와 이유를 알려 준다. 안전성이 확실한 HBCS004의 nameof 치환만 Code Fix를 제공한다.

처음 적용하는 4단계

새 프로젝트든 기존 프로젝트든 아래 순서대로 진행하면 된다. 처음에는 경고를 모두 오류로 바꾸지 말고, 팀이 받아들일 수 있는 기준부터 시작하는 편이 좋다.

.NET 확인

터미널에서 SDK를 확인한다.

Analyzer 연결

개발 중에는 프로젝트 참조를 추가한다.

규칙 파일 작성

프로젝트 루트에 .editorconfig를 둔다.

검증 실행

format, build, test 순서로 확인한다.

1. 준비 확인

PowerShell을 열어 다음을 실행한다. 이 저장소는 .NET SDK 10.0.400을 기준으로 한다.

dotnet --version
dotnet restore CSharpRuleKeeper.sln

2. 내 프로젝트에 Analyzer 연결

가장 쉬운 방법은 소비 프로젝트의 .csproj 파일에 이 저장소의 Analyzer 프로젝트를 연결하는 것이다. Include 경로는 현재 프로젝트에서 이 저장소로 가는 실제 경로로 바꾼다.

<ItemGroup>
  <ProjectReference Include="..\CSharpRuleKeeper\src\CSharpRuleKeeper.Analyzers\CSharpRuleKeeper.Analyzers.csproj"
                    OutputItemType="Analyzer"
                    ReferenceOutputAssembly="false" />
</ItemGroup>
⚠️
패키지 참조는 언제 쓰는가
PackageReference는 CSharpRuleKeeper 패키지가 NuGet 원본에 게시되어 있을 때 쓴다. 아직 원본이 없다면 위의 프로젝트 참조가 정확한 시작 방법이다.

3. 기본 규칙 파일 만들기

소비 프로젝트의 최상위 폴더에 .editorconfig를 새로 만들고 아래 내용을 붙여 넣는다. 기존 파일이 있다면 전체를 덮어쓰지 말고 C# 구역과 personal_csharp_rules 항목을 비교하여 합친다.

root = true

[*.{cs,csx}]
indent_style = space
indent_size = 4
csharp_new_line_before_open_brace = all
csharp_prefer_braces = true:error

personal_csharp_rules.method_lines_warning = 30
personal_csharp_rules.method_lines_error = 100
personal_csharp_rules.type_lines_warning = 300
personal_csharp_rules.type_lines_error = 500
personal_csharp_rules.max_line_length = 120
personal_csharp_rules.allow_magic_numbers = -1,0,1,2
personal_csharp_rules.analyze_test_projects = false
personal_csharp_rules.public_field_allowed_attributes =
personal_csharp_rules.type_length_excluded_suffixes =

4. 검사 실행

이 저장소를 수정하는 경우에는 품질 게이트 하나로 검사한다. 기본 모드는 확인만 하며 파일을 고치지 않는다.

.\build\run-quality-gate.ps1 -Solution .\CSharpRuleKeeper.sln

가장 중요한 부분: 내 코딩 스타일 준비와 설정

좋은 규칙은 "좋아 보이는 규칙"이 아니라 팀이 매일 지킬 수 있고, 도구가 오해 없이 판단할 수 있는 규칙이다. 아래의 세 층으로 나누어 준비하면 적용이 쉬워진다.

① 서식

공백, 들여쓰기, 중괄호 위치처럼 의미를 바꾸지 않는 항목이다. .editorconfig와 dotnet format에 둔다.

② 검사 규칙

public 필드, 긴 메서드, 매직 넘버처럼 코드 의미를 봐야 하는 항목이다. HBCS Analyzer가 검사한다.

③ 사람의 판단

설계 분리, API 변경, 직렬화 계약은 자동으로 바꾸지 않는다. 진단을 보고 의도를 확인한다.

규칙을 적기 전에 답할 질문

  • 이 규칙은 모든 프로젝트에 적용할 것인가, 특정 폴더에만 적용할 것인가.
  • 위반을 즉시 막을 것인가(error), 우선 알려 줄 것인가(warning).
  • 자동 생성 파일, 테스트, DTO, 마이그레이션처럼 합리적인 예외가 있는가.
  • 위반을 자동으로 바꾸어도 API와 동작이 그대로 유지되는가.

예시: 팀 스타일로 조정하기

아래 예시는 메서드와 줄 길이를 조금 완화하고, 도메인에서 자주 쓰는 숫자와 상호 운용 public 필드 예외를 명시한다. 쉼표로 여러 값을 적을 수 있다.

[*.cs]
# 길이는 선언의 첫 토큰부터 마지막 토큰까지의 실제 줄 수다.
personal_csharp_rules.method_lines_warning = 40
personal_csharp_rules.method_lines_error = 120
personal_csharp_rules.type_lines_warning = 350
personal_csharp_rules.type_lines_error = 550
personal_csharp_rules.max_line_length = 140

# 의도가 자명한 숫자만 추가한다.
personal_csharp_rules.allow_magic_numbers = -1,0,1,2,100,404

# 상호 운용/직렬화 목적으로 허용할 특성 이름이다.
personal_csharp_rules.public_field_allowed_attributes = StructLayout,DataMember

# 생성에 가까운 타입은 접미사로 길이 검사를 제외할 수 있다.
personal_csharp_rules.type_length_excluded_suffixes = Dto,Migration
🧭
폴더별로 다르게 설정할 수 있다
예를 들어 tests 폴더 아래에 별도 .editorconfig를 만들고 personal_csharp_rules.analyze_test_projects = true를 쓰면 테스트에서도 매직 넘버를 검사할 수 있다. 하위 파일의 설정이 더 가까운 범위에서 적용된다.

안전한 도입 순서

  1. 기존 코드를 먼저 빌드하고 현재 경고 수를 기록한다.
  2. 서식과 public 필드 같은 명확한 규칙부터 적용한다.
  3. 긴 메서드·타입은 경고로 시작해 실제 예외를 수집한다.
  4. 예외가 반복되면 코드에 억지 주석을 붙이기보다 `.editorconfig`에 근거와 함께 설정한다.
  5. 팀이 안정적으로 지키게 된 규칙만 오류 처리 범위를 넓힌다.

어떤 진단이 나오는가

진단 ID는 HBCS로 시작한다. 빌드 출력에서 ID를 검색하면 어떤 정책 때문인지 빠르게 알 수 있다.

ID내용기본값
HBCS001public 필드를 금지한다. 명시한 특성이 필드 또는 포함 타입에 있으면 예외다.error
HBCS002–003bool는 상태 접두사를, 컬렉션은 복수형 이름을 사용한다.warning
HBCS004확인 가능한 매개변수·멤버 문자열은 nameof를 사용한다.warning
HBCS005이름 없는 숫자를 상수·열거형·설명적 변수로 꺼낸다.warning
HBCS006–007메서드/타입의 실제 줄 수 한계를 검사한다.warning/error
HBCS008–010불필요한 private, 줄 끝 주석, 연속 빈 줄을 검사한다.info/warning
HBCS011–014정수 타입 표기, 줄 길이, 특수 타입·비동기 명명, 필드 접두사를 검사한다.warning/error

진단을 읽고 고치는 예시

문제 있는 코드
public int count;
bool ready;

throw new ArgumentNullException("value");
→
의도가 드러나는 코드
private Int32 _count;
Boolean isReady;

throw new ArgumentNullException(nameof(value));

위 예시처럼 int는 HBCS011에 따라 Int32로, private 필드는 HBCS014에 따라 _camelCase로 바꾼다. nameof는 실제 매개변수 또는 멤버가 존재하는 문맥에서만 사용한다. JSON 키나 외부 프로토콜 문자열을 이름 변경에 맞춰 자동으로 바꾸면 안 된다.

AI 코딩 에이전트와 같이 쓰기

AI가 코드를 수정한 뒤에도 사람이 작성한 코드와 같은 검사를 거치게 하면 규칙이 일관된다. 작업 완료 훅에는 품질 게이트 명령 하나만 연결한다.

powershell -NoProfile -ExecutionPolicy Bypass -File .\build\run-quality-gate.ps1 -Solution .\MySolution.sln
AI 작업 완료파일 변경이 끝난 시점에 훅을 실행한다.
품질 게이트서식 확인 → 빌드 → 테스트를 실행한다.
결과 처리HBCS 위치를 고친 뒤 최대 2~3회 재검증한다.
🛡️
자동 포맷은 기본 훅에서 실행하지 않는다
기본 품질 게이트는 --verify-no-changes로 확인만 한다. 서식을 실제 적용하려는 경우에만 사람이 -Fix를 명시한다. 린트 통과만을 위해 public API, 직렬화 형식, 외부 문자열, 예외 동작을 바꾸지 않는다.

자주 막히는 지점

Analyzer가 보이지 않는다

.csproj의 ProjectReference 경로와 OutputItemType="Analyzer"를 확인한다. 그 다음 dotnet restore와 dotnet build를 다시 실행한다.

서식 검사만 실패한다

변경을 검토한 뒤에만 run-quality-gate.ps1 -Fix를 실행한다. 검증 훅에서 자동으로 고치지 않는다.

매직 넘버가 너무 많이 나온다

먼저 경고로 유지한다. 정말 의미가 고정된 값만 allow_magic_numbers에 추가하고, 나머지는 이름 있는 상수 또는 열거형으로 바꾼다.

기존 코드가 너무 많다

길이·명명 규칙은 경고로 시작한다. 새로 수정하는 파일부터 정리하고, 예외를 확인한 뒤 점진적으로 강화한다.

마지막 확인 목록

  • Analyzer 프로젝트 또는 배포된 패키지를 소비 프로젝트에 연결했다.
  • 프로젝트 루트의 .editorconfig에 팀 기준과 예외를 적었다.
  • 예외는 "왜 필요한가"를 설명할 수 있는 최소 범위로 제한했다.
  • 기본 검증과 자동 포맷의 역할을 분리했다.
  • 빌드와 테스트를 통과시킨 뒤 규칙 강도를 조정했다.
