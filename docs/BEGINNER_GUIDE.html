현재 실행 계약부터 확인하기

먼저 -Doctor로 dotnet·SDK·PowerShell·대상 global.json을 읽기 전용으로 확인한다. 이 저장소 개발은 SDK 10.0.400 feature band와 latestFeature roll-forward를 사용하고, 대상은 대상 프로젝트 자체 SDK로 빌드한다.

powershell -NoProfile -ExecutionPolicy Bypass -File "C:\tools\CSharpRuleKeeper\build\Invoke-CSharpRuleKeeper.ps1" -Doctor -Solution ".\MySolution.sln"

기본 검사는 dotnet format whitespace --verify-no-changes이며 파일을 바꾸지 않는다. -Fix는 whitespace만 적용하고 이름·API·외부 Code Fix를 실행하지 않는다. Markdown과 JSON이 함께 생성되며, HBCS 0개라도 JSON의 analysisCompleted가 false면 완료가 아니다. 종료 코드는 통과 0, 정책 위반 1, 실행·설정·미완료 2다.

💡
점진적 도입
도입 설정과 기준선을 검토한다. 설정 예제는 자동 적용되지 않으며 TreatWarningsAsErrors 대상은 warning도 실패할 수 있다. 15개 규칙의 예외·경계·계약 위험은 참조 안내에서 이어서 확인한다.

가장 짧은 사용 순서

  1. PowerShell을 열고 검사할 솔루션이 있는 폴더로 이동한다.
  2. 명령에서 도구 경로와 -Solution 값만 내 환경에 맞게 바꾼다.
  3. 명령을 실행하고 생성된 Markdown 보고서를 읽는다.
  4. 코드를 수정한 뒤 같은 명령을 다시 실행해 HBCS 진단 수가 0인지 확인한다.

컴파일 상수로 위반 코드를 켜고 검사한다.

보고서 읽기

HBCS001과 HBCS002의 위치와 수정 방향을 확인한다.

재검사

같은 명령으로 HBCS 진단 수가 0인지 확인한다.

1. 의도적인 실패를 실행한다

이 명령의 실패는 정상이다. sample-practice-report.md에 두 진단과 수정 방법이 기록된다.

HBCS001과 HBCS002가 사라지면 연습이 끝난다. 다시 연습하고 싶으면 수정한 샘플 코드를 되돌린 뒤 같은 명령을 실행한다.

무엇을 해 주는 도구인가

CSharpRuleKeeper는 C# 규칙을 검사하고, HBCS 진단 위치와 수정 방법을 Markdown으로 정리하는 도구다.

1. 코드 작성사람 또는 AI가 C# 코드를 수정한다.
2. 명령 실행검사할 솔루션 또는 프로젝트를 지정한다.
3. 수정 지침HBCS 위치와 수정 방법을 Markdown으로 확인한다.

독립 실행 도구 사용법: 4단계

아래 절차는 내가 직접 수정한 코드와 코딩 에이전트가 수정한 코드를 모두 검사하는 방법이다. 먼저 검사하고, 보고서를 읽어 고친 뒤, 같은 명령으로 다시 확인한다.

도구 경로 확인

도구 저장소의 실제 경로를 정한다.

대상 지정

검사할 솔루션 또는 프로젝트 경로를 정한다.

보고서 생성

명령으로 HBCS 수정 지침 Markdown을 만든다.

수정 후 재검사

보고서가 비워질 때까지 같은 명령을 실행한다.

1. 준비하기

PowerShell을 열고 .NET SDK를 확인한다. 아래 예시의 C:\tools\CSharpRuleKeeper는 이 도구 저장소의 실제 경로로 바꾼다.

dotnet --version

2. 사례 1: 내가 수정한 솔루션 검사하기

대상 솔루션의 루트에서 다음 명령을 실행한다. 대상의 .csproj는 수정하지 않으며, 보고서에 진단 위치와 수정 방법이 기록된다.

powershell -NoProfile -ExecutionPolicy Bypass -File C:\tools\CSharpRuleKeeper\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -OutputPath .\coding-agent-change-report.md

3. 사례 2: 코딩 에이전트의 변경 검토하기

위 명령으로 생성된 coding-agent-change-report.md를 에이전트에게 읽게 한다. 에이전트는 각 위치의 문맥을 확인해 수정하고, 같은 명령을 다시 실행한다. HBCS 진단 수가 0이면 규칙 검사가 끝난다.

⚠️
보고서의 수정 방법은 안전 경계다
린트 통과만을 위해 public API, 직렬화 형식, 외부 프로토콜 문자열, 예외 동작을 바꾸면 안 된다. 메서드와 타입의 길이는 책임 분리로 해결한다.

4. 사례 3: 서식을 적용한 뒤 검사하기

서식 파일 변경에 동의한 경우에만 -Fix를 추가한다. 이 옵션은 dotnet format만 적용하며, 의미를 판단해야 하는 린트 수정은 자동으로 하지 않는다.

powershell -NoProfile -ExecutionPolicy Bypass -File C:\tools\CSharpRuleKeeper\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -OutputPath .\coding-agent-change-report.md -Fix
💡
규칙 값을 조정하고 싶다면
대상 솔루션의 .editorconfig에서 줄 수, 허용 숫자, 예외를 조정할 수 있다. 이 파일은 선택 사항이며 도구를 참조하기 위한 프로젝트 설정이 아니다.

가장 중요한 부분: 내 코딩 스타일 준비와 설정

좋은 규칙은 "좋아 보이는 규칙"이 아니라 팀이 매일 지킬 수 있고, 도구가 오해 없이 판단할 수 있는 규칙이다. 아래의 세 층으로 나누어 준비하면 적용이 쉬워진다.

① 서식

공백, 들여쓰기, 중괄호 위치처럼 의미를 바꾸지 않는 항목이다. .editorconfig와 dotnet format에 둔다.

② 검사 규칙

public 필드, 긴 메서드, 매직 넘버처럼 코드 의미를 봐야 하는 항목이다. HBCS Analyzer가 검사한다.

③ 사람의 판단

설계 분리, API 변경, 직렬화 계약은 자동으로 바꾸지 않는다. 진단을 보고 의도를 확인한다.

규칙을 적기 전에 답할 질문

  • 이 규칙은 모든 프로젝트에 적용할 것인가, 특정 폴더에만 적용할 것인가.
  • 위반을 즉시 막을 것인가(error), 우선 알려 줄 것인가(warning).
  • 자동 생성 파일, 테스트, DTO, 마이그레이션처럼 합리적인 예외가 있는가.
  • 위반을 자동으로 바꾸어도 API와 동작이 그대로 유지되는가.

예시: 팀 스타일로 조정하기

아래 예시는 메서드와 줄 길이를 조금 완화하고, 도메인에서 자주 쓰는 숫자와 상호 운용 public 필드 예외를 명시한다. 쉼표로 여러 값을 적을 수 있다.

[*.cs]
# 길이는 선언의 첫 토큰부터 마지막 토큰까지의 실제 줄 수다.

personal_csharp_rules.method_lines_error = 120
personal_csharp_rules.type_lines_warning = 350
personal_csharp_rules.type_lines_error = 550
personal_csharp_rules.max_line_length = 140

# 의도가 자명한 숫자만 추가한다.
personal_csharp_rules.allow_magic_numbers = -1,0,1,2,100,404

# 상호 운용/직렬화 목적으로 허용할 특성 이름이다.
personal_csharp_rules.public_field_allowed_attributes = StructLayout,DataMember

# 생성에 가까운 타입은 접미사로 길이 검사를 제외할 수 있다.
personal_csharp_rules.type_length_excluded_suffixes = Dto,Migration
🧭
폴더별로 다르게 설정할 수 있다
예를 들어 tests 폴더 아래에 별도 .editorconfig를 만들고 personal_csharp_rules.analyze_test_projects = true를 쓰면 테스트에서도 매직 넘버를 검사할 수 있다. 하위 파일의 설정이 더 가까운 범위에서 적용된다.

클래스 크기 제한을 바꾸는 예시

아래처럼 경고 기준과 오류 기준을 함께 적는다. 오류 기준은 경고 기준보다 커야 한다. 그렇지 않으면 기본값으로 돌아간다.

[*.cs]

personal_csharp_rules.method_lines_warning = 40

# 한 물리 줄은 141자부터 경고가 된다.

💡
파일 전체 크기도 제한할 수 있다
file_lines_warning과 file_lines_error는 주석과 빈 줄을 포함한 한 .cs 파일 전체의 실제 줄 수를 검사한다. 기본값은 500줄 경고, 1000줄 초과 오류다.

안전한 도입 순서

  1. 기존 코드를 먼저 빌드하고 현재 경고 수를 기록한다.
  2. 서식과 public 필드 같은 명확한 규칙부터 적용한다.
  3. 긴 메서드·타입은 경고로 시작해 실제 예외를 수집한다.
  4. 예외가 반복되면 코드에 억지 주석을 붙이기보다 .editorconfig에 근거와 함께 설정한다.
  5. 팀이 안정적으로 지키게 된 규칙만 오류 처리 범위를 넓힌다.

어떤 진단이 나오는가

진단 ID는 HBCS로 시작한다. 빌드 출력에서 ID를 검색하면 어떤 정책 때문인지 빠르게 알 수 있다.

ID내용기본값
HBCS001public 필드를 금지한다. 명시한 특성이 필드 또는 포함 타입에 있으면 예외다.error
HBCS002–003bool는 상태 접두사를, 컬렉션은 복수형 이름을 사용한다.warning
HBCS004확인 가능한 매개변수·멤버 문자열은 nameof를 사용한다.warning
HBCS005이름 없는 숫자를 상수·열거형·설명적 변수로 꺼낸다.warning
HBCS006–007메서드/타입의 실제 줄 수 한계를 검사한다.warning/error
HBCS008–010불필요한 private, 줄 끝 주석, 연속 빈 줄을 검사한다.info/warning
HBCS011–014정수 타입 표기, 줄 길이, 특수 타입·비동기 명명, 필드 접두사를 검사한다.warning/error

진단을 읽고 고치는 예시

문제 있는 코드
public int count;
bool ready;

throw new ArgumentNullException("value");
→
의도가 드러나는 코드
private Int32 _count;
Boolean isReady;

throw new ArgumentNullException(nameof(value));

위 예시처럼 int는 HBCS011에 따라 Int32로, private 필드는 HBCS014에 따라 _camelCase로 바꾼다. nameof는 실제 매개변수 또는 멤버가 존재하는 문맥에서만 사용한다. JSON 키나 외부 프로토콜 문자열을 이름 변경에 맞춰 자동으로 바꾸면 안 된다.

AI 코딩 에이전트와 같이 쓰기

AI가 코드를 수정한 뒤 독립 실행 도구를 호출하면, 대상 프로젝트 파일을 바꾸지 않고도 사람이 작성한 코드와 같은 규칙으로 검사할 수 있다. 작업 완료 훅에는 아래 명령을 연결한다.

powershell -NoProfile -ExecutionPolicy Bypass -File C:\tools\CSharpRuleKeeper\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -OutputPath .\coding-agent-change-report.md
AI 작업 완료파일 변경이 끝난 시점에 도구를 실행한다.
독립 검사실행 중에만 Analyzer를 빌드에 주입한다.
결과 처리Markdown의 HBCS 위치와 수정 방법을 읽고 재검사한다.
🛡️
자동 포맷은 명시한 경우에만 적용한다
기본 명령은 검사만 한다. 서식을 실제 적용하려는 경우에만 사람이 -Fix를 명시한다. 린트 통과만을 위해 public API, 직렬화 형식, 외부 문자열, 예외 동작을 바꾸지 않는다.

자주 막히는 지점

도구가 실행되지 않는다

C:\tools\CSharpRuleKeeper 경로와 Invoke-CSharpRuleKeeper.ps1 파일 이름을 확인한다. 대상 솔루션은 존재하는 .sln 또는 .csproj 경로여야 한다.

서식을 적용하고 싶다

변경을 검토한 뒤에만 독립 실행 명령에 -Fix를 추가한다. 기본 검사나 훅에서 자동으로 고치지 않는다.

매직 넘버가 너무 많이 나온다

먼저 경고로 유지한다. 정말 의미가 고정된 값만 allow_magic_numbers에 추가하고, 나머지는 이름 있는 상수 또는 열거형으로 바꾼다.

기존 코드가 너무 많다

길이·명명 규칙은 경고로 시작한다. 새로 수정하는 파일부터 정리하고, 예외를 확인한 뒤 점진적으로 강화한다.

마지막 확인 목록

  • 대상 프로젝트 파일을 수정하지 않고 독립 실행 명령을 실행했다.
  • 생성된 coding-agent-change-report.md의 위치와 수정 방법을 확인했다.
  • 예외는 "왜 필요한가"를 설명할 수 있는 최소 범위로 제한했다.
  • 기본 검사와 자동 포맷의 역할을 분리했다.
  • 수정 후 같은 명령을 다시 실행해 HBCS 진단 수를 확인했다.

💡
파일 크기와 타입 크기는 함께 적용된다
한 파일 안의 큰 class·struct·interface·record는 type_lines_*로, 파일 전체의 크기는 file_lines_*로 각각 검사한다. 두 기준을 모두 넘으면 두 진단이 함께 나올 수 있다.
