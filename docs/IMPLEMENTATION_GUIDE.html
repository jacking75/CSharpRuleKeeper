CSharpRuleKeeper 구현 안내

이 도구가 어떤 순서로 코드를 검사하는지, 규칙을 어떻게 추가하는지 쉬운 말로 설명한다. 도구를 처음 사용하는 방법은 초보자 안내를 참고한다.

개요용어 먼저 보기구성검사 흐름규칙 구현규칙 추가검증

무엇을 구현했는가

CSharpRuleKeeper는 C# 코드가 팀의 규칙을 지키는지 확인하는 도구다. 검사할 프로젝트 파일은 건드리지 않고, 검사할 때만 필요한 규칙 검사기를 잠시 연결한다.

가장 중요한 구분이다. dotnet format whitespace는 공백·들여쓰기·줄바꿈처럼 뜻이 바뀌지 않는 모양만 확인하거나 정리한다. Roslyn Analyzer는 public 필드, 이름, 메서드 길이처럼 코드의 뜻을 이해해야 판단할 수 있는 규칙을 검사한다. API, 저장 형식, 실행 순서가 바뀔 수 있는 수정은 자동으로 하지 않는다.

코드 모양

.editorconfig는 “4칸 들여쓰기” 같은 약속을 적는 설정 파일이다. dotnet format은 그 약속을 확인한다.

코드 의미

Analyzer는 컴파일러가 이해한 코드 구조를 읽는 작은 검사 프로그램이다. HBCS001~HBCS015 진단을 알려 준다.

검사 결과

Markdown 보고서는 사람이 읽는다. JSON과 SARIF는 다른 프로그램이나 자동화가 읽기 쉬운 구조화 결과다.

다른 프로젝트를 검사할 때 일어나는 일

  1. -Doctor는 설치된 .NET 도구와 대상 프로젝트가 요구하는 SDK를 읽기만 확인한다. 코드나 설정을 바꾸지 않는다.
  2. 기본 실행은 dotnet format whitespace --verify-no-changes로 코드 모양이 약속과 맞는지 확인한다. --verify-no-changes는 “고치지 말고 확인만 하라”는 뜻이다. -Fix를 붙였을 때만 공백·들여쓰기 서식을 적용한다.
  3. 실행기는 규칙 검사기 파일을 준비한 뒤, 임시 빌드 설정을 이용해 이번 한 번의 빌드에만 연결한다.
  4. 대상 프로젝트는 원래 사용하던 SDK와 .NET 버전으로 빌드한다. SARIF 파일과 완료 marker를 확인해 규칙 검사가 중간에 빠지지 않았는지 확인한다.
  5. 결과는 사람이 읽는 Markdown과 다른 프로그램이 읽는 JSON으로 저장한다. 진단이 0개여도 analysisCompleted가 거짓이면 검사가 끝난 것이 아니다.
powershell -NoProfile -ExecutionPolicy Bypass -File .\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -OutputPath .\coding-agent-change-report.md
검사 대상은 그대로 둔다. ProjectReference와 PackageReference는 프로젝트가 다른 코드나 패키지를 계속 참조하게 만드는 설정이다. CSharpRuleKeeper는 이 설정이나 targets 파일을 대상 프로젝트에 추가하지 않는다. 검사에 필요한 연결은 실행이 끝나면 사라지는 임시 설정으로만 만든다.

Analyzer와 Code Fix 구현 원칙

새 규칙은 Analyzer라는 C# 클래스로 만든다. Analyzer는 코드를 실행하지 않고 컴파일러가 만든 코드 구조를 읽어 “여기가 규칙 위반이다”라고 알려 준다. 각 규칙에는 HBCS001처럼 고유한 번호를 붙여, 보고서와 문서에서 같은 규칙을 가리키게 한다.

아래 코드는 새 Analyzer가 갖춰야 할 기본 모양이다. 지금 당장 외울 필요는 없다. ConfigureGeneratedCodeAnalysis는 도구가 자동으로 만든 파일을 검사하지 않게 하고, EnableConcurrentExecution은 여러 파일을 더 빠르게 검사하게 한다.

[DiagnosticAnalyzer(LanguageNames.CSharp)]
public sealed class ExampleAnalyzer : DiagnosticAnalyzer
{
    public override void Initialize(AnalysisContext context)
    {
        context.ConfigureGeneratedCodeAnalysis(GeneratedCodeAnalysisFlags.None);
        context.EnableConcurrentExecution();
        context.RegisterSyntaxNodeAction(AnalyzeNode, SyntaxKind.MethodDeclaration);
    }
}

코드 구조와 이름

컴파일러가 알려 주는 “이 변수는 무엇인가” 정보를 함께 확인한다. 그래서 단순히 글자를 검색하는 것보다 오탐이 적다.

줄 수

메서드와 타입은 시작부터 끝까지 실제 줄을 센다. 주석과 빈 줄도 읽는 부담에 포함되므로 함께 센다.

프로젝트별 설정

personal_csharp_rules.*는 프로젝트마다 한계와 예외를 정하는 .editorconfig 항목이다. 잘못된 값은 안전한 기본값으로 되돌린다.

자동 수정의 한계

수정 후에도 뜻이 같다는 확신이 있을 때만 Code Fix를 제공한다. public 필드 변경, 큰 리팩터링, 프로토콜 문자열 변경은 사람이 결정한다.

새 규칙을 추가하는 순서

  1. RuleIds.cs에 새 HBCS 번호를 추가한다. 번호는 보고서에서 규칙을 찾는 주소이므로, 공개한 뒤에는 뜻과 심각도를 함부로 바꾸지 않는다.
  2. RuleDefinitions.cs에 사용자에게 보일 제목과 메시지를 적는다. 메시지에는 실제 줄 수나 한계처럼 고치는 데 필요한 값을 넣는다. 새 규칙은 보통 warning부터 시작한다.
  3. 가장 알맞은 폴더에 Analyzer 클래스를 만들고, 자동 생성 파일은 제외한다. 프로젝트마다 바꿀 값이 있으면 AnalyzerOptionsReader에 읽는 방법을 추가한다.
  4. “문제 없는 코드”, “위반 코드”, “예외 코드”, “한계 바로 앞뒤 코드”를 자동 테스트에 넣는다. 자동 수정이 있다면 고친 뒤에도 다시 검사해 문제가 없는지 확인한다.
  5. 참조 안내, 두 README, 초보자 안내의 규칙 표·설명을 현재 동작에 맞춰 갱신한다.
  6. 아래 검증 명령을 실행하고, 다른 프로젝트를 검사해도 그 프로젝트 파일이 바뀌지 않는지 확인한다.

저장소 개발 검증

소스 또는 규칙 설정을 변경한 뒤에는 저장소 루트에서 다음을 실행한다. 품질 게이트는 단위 테스트 외에도 외부 프로젝트 주입, 실패 분류, 서식, 보고서 계약을 검사한다.

dotnet format --verify-no-changes
dotnet build
dotnet test
.\build\run-quality-gate.ps1
  • dotnet format --verify-no-changes는 코드 모양이 규칙과 맞는지만 확인한다.
  • dotnet build는 C# 코드가 컴파일되는지 확인한다.
  • dotnet test는 자동 테스트가 기대한 대로 동작하는지 확인한다.
  • run-quality-gate.ps1는 위 확인과 외부 프로젝트 검사 시나리오를 한 번 더 묶어 실행한다.

작업 완료 훅은 build/run-quality-gate.ps1만 호출한다. 기본값은 검증이며 사용자 동의 없이 작업 트리를 자동 포맷하지 않는다. CI 구성·수정은 명시적 요청이 있을 때만 한다.
