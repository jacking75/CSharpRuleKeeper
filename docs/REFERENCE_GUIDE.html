CSharpRuleKeeper 참조 안내

규칙, 설정, 기존 코드 도입, 실행 결과, 호환성 정보를 한곳에 모은 안내서다. 처음 사용하는 경우에는 초보자 안내부터 읽는다.

시작·호환성규칙옵션도입·기준선보고서문제 해결배포

시작하기와 호환성

대상 프로젝트의 파일을 바꾸지 않고 검사한다. 대상은 자체 SDK와 TFM으로 빌드되므로 필요한 SDK는 대상 환경에 설치되어 있어야 한다. 처음에는 아래 -Doctor 명령으로 내 환경에서 실행할 수 있는지만 확인한다.

powershell -NoProfile -ExecutionPolicy Bypass -File .\build\Invoke-CSharpRuleKeeper.ps1 -Doctor -Solution .\MySolution.sln

처음 실행하기 전에 확인할 세 가지

  1. 도구 위치를 정한다. 위 명령의 .\build\Invoke-CSharpRuleKeeper.ps1은 CSharpRuleKeeper 폴더 안의 실행 파일이다. 다른 위치에서 실행하면 실제 경로로 바꾼다.
  2. 검사 대상을 정한다. .\MySolution.sln을 검사할 솔루션(.sln) 또는 프로젝트(.csproj) 경로로 바꾼다.
  3. Doctor 결과를 읽는다. 필요한 dotnet과 SDK가 보이면 다음 검사로 진행한다. 누락되었다면 먼저 대상 프로젝트가 요구하는 SDK를 설치하거나 경로를 바로잡는다.
안전한 첫 실행이다. -Doctor는 코드, 프로젝트 파일, .editorconfig, 패키지를 바꾸지 않는다. 문제를 고치기 전에 환경만 읽어 확인한다.

실제 검사를 실행하는 명령

powershell -NoProfile -ExecutionPolicy Bypass -File .\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -OutputPath .\coding-agent-change-report.md

검사가 끝나면 지정한 Markdown 보고서와 같은 이름의 JSON 결과가 만들어진다. 기본값은 확인만 하며, 코드 모양도 자동으로 고치지 않는다. 공백·들여쓰기 정리를 실제로 적용하려면 결과를 검토한 뒤에만 -Fix를 추가한다.

규칙

진단은 HBCS001~HBCS015다. 자동 수정은 의미 보존이 명확한 HBCS004에만 제공한다. 나머지는 API·직렬화·예외·제어 흐름 계약을 검토한 뒤 수동으로 고친다.

진단을 읽고 고치는 순서

순서할 일이유
1보고서의 HBCS 번호, 파일, 줄, 메시지를 읽는다.같은 종류의 규칙이라도 실제 위반 위치와 이유가 다를 수 있다.

3이름·필드·문자열을 바꾸기 전 외부에서 쓰는 API, JSON, 데이터베이스, reflection 연결을 확인한다.규칙을 통과해도 외부 계약을 깨뜨리면 올바른 수정이 아니다.
4코드를 고친 뒤 같은 명령을 다시 실행한다.한 번의 수정으로 다른 규칙이나 빌드 오류가 생기지 않았는지 확인한다.
심각도 읽는 법이다. error는 기본적으로 실패로 처리한다. warning은 개선이 필요한 신호이며, 프로젝트의 TreatWarningsAsErrors 설정이 켜져 있으면 실패가 될 수 있다. info는 개선 제안이다.

HBCS003컬렉션 이름을 복수형으로 권고한다. warningstring, override, 인터페이스 구현은 제외한다.자연어 판정에는 한계가 있으므로 외부 이름은 신중히 바꾼다.
HBCS004확인 가능한 식별자 문자열에 nameof를 요구한다. warning예외 paramName, 속성 변경 통지, 현재 타입 reflection만 검사한다.IDE Code Fix와 Fix All을 제공한다. JSON 키·프로토콜 문자열은 바꾸지 않는다.
HBCS005설명 없는 매직 넘버를 경고한다. warningconst, enum, 특성, bit flag, 기본 테스트 어셈블리는 제외한다. 기본 허용값은 -1,0,1,2다.allow_magic_numbers, analyze_test_projects. 값은 바꾸지 않고 이름을 추출한다.

HBCS007타입 물리 줄 수를 제한한다. 300줄 초과 warning, 500줄 초과 error생성 코드, EF Migration 파생 타입, 설정한 접미사는 제외한다.type_lines_warning, type_lines_error, type_length_excluded_suffixes.
HBCS008중복된 private 표기를 알린다. infoprivate이 기본 접근성이 아닌 문맥은 제외한다.접근성을 바꾸지 않고 토큰만 제거한다.
HBCS009줄 끝 주석을 금지한다. warningXML 문서 주석과 독립 주석은 허용한다.주석 내용을 보존해 독립 줄로 옮긴다.

HBCS011명시적 비트폭 정수 이름을 요구한다. warningint, long, uint, ulong만 검사한다.CLR 형식은 같지만 팀 관례와 충돌할 수 있다.

HBCS013인터페이스, Attribute, 기반 타입, 비동기 메서드 명명 패턴을 요구한다. warningMain, override, 인터페이스 구현은 제외한다. 비동기는 Task/ValueTask 반환을 검사한다.공개 이름 변경 전 계약을 확인한다.
HBCS014필드 저장 방식별 접두사를 요구한다. error인스턴스 _, static s_, ThreadStatic t_ 뒤 camelCase를 요구한다.reflection·직렬화가 비공개 이름을 쓰는지 확인한다.

문제 해결과 제보

먼저 -Doctor로 실행 환경을 확인하고, 빌드 실패 또는 HBCS 진단 0개를 분석 완료로 오해하지 않는다. JSON의 analysisCompleted와 executionErrors를 함께 확인한다.

보이는 결과먼저 할 일
SDK 또는 dotnet을 찾지 못한다.-Doctor 출력에서 대상 프로젝트가 요구하는 SDK 버전을 확인한다. 해당 SDK를 설치한 뒤 같은 명령을 다시 실행한다.
HBCS 진단은 0개인데 검사에 실패한다.JSON의 analysisCompleted와 executionErrors를 확인한다. 서식, 빌드, 보고서 생성, 분석 완료 확인 중 하나가 실패했을 수 있다.
warning 때문에 빌드가 실패한다.프로젝트의 TreatWarningsAsErrors 설정을 확인한다. 규칙을 없애기보다 우선 해당 규칙을 고칠지, 팀의 도입 설정을 조정할지 결정한다.
규칙이 외부 계약을 바꾸라고 제안하는 것처럼 보인다.자동 수정하지 않는다. 참조하는 코드, 직렬화 형식, 외부 프로토콜을 확인하고 예외 설정 또는 수동 설계를 선택한다.
재현 가능한 정보만 공유한다. 제보에는 도구 버전, 운영체제, SDK, PowerShell, 실행 명령, 관련 .editorconfig, 최소 재현 코드, 예상·실제 진단을 포함한다. 비공개 전체 소스, 토큰, 사용자 경로가 담긴 불필요한 로그는 공유하지 않는다.

응답 시간 SLA는 제공하지 않으며, 재현 가능한 범위에서 유지보수한다.

.editorconfig 옵션

지원 옵션은 아래 11개다. 파일별 최종값은 Roslyn의 가까운 .editorconfig 우선순위로 결정한다. 검사 없이 최신 카탈로그를 보려면 -ExplainEditorConfig를 사용한다.

powershell -NoProfile -ExecutionPolicy Bypass -File .\build\Invoke-CSharpRuleKeeper.ps1 -ExplainEditorConfig

처음 적용할 때 복사할 수 있는 작은 설정

아래는 기본값을 명시해 두는 시작점이다. 대상 프로젝트의 기존 .editorconfig에 필요한 줄만 추가한다. 이 파일을 새로 만들거나 바꾸기 전에는 팀의 기존 서식 설정과 충돌하지 않는지 확인한다.

[*.cs]
personal_csharp_rules.method_lines_warning = 30
personal_csharp_rules.method_lines_error = 100
personal_csharp_rules.type_lines_warning = 300
personal_csharp_rules.type_lines_error = 500
personal_csharp_rules.file_lines_warning = 500
personal_csharp_rules.file_lines_error = 1000
personal_csharp_rules.max_line_length = 120
personal_csharp_rules.allow_magic_numbers = -1,0,1,2
personal_csharp_rules.analyze_test_projects = false

method_lines_warning30HBCS006 경고 한계
method_lines_error100HBCS006 오류 한계
type_lines_warning300HBCS007 경고 한계
type_lines_error500HBCS007 오류 한계

길이 warning/error는 양수이고 warning < error여야 한다. 잘못된 쌍은 해당 기본값으로 복원하며, 파일은 자동 수정하지 않는다.

점진적 도입과 기준선

config/presets/personal.editorconfig는 개인 기본 정책이고, team-starter.editorconfig는 계약 안전 규칙을 먼저 켜는 검토용 예제다. preset은 자동으로 복사하거나 기존 설정을 덮어쓰지 않는다.

TreatWarningsAsErrors=true인 대상에서는 warning도 빌드를 실패시킬 수 있다. HBCS006·007·015는 ID severity를 바꾸는 대신 위의 warning/error 한계를 조정해야 두 단계 의미를 유지할 수 있다.

기존 코드에 안전하게 적용하는 순서

  1. 먼저 읽기 전용 검사를 한다. 얼마나 많은 진단이 있는지 보고, 어떤 규칙이 실제로 부담이 되는지 파악한다.
  2. 계약 안전 규칙부터 고른다. public 필드나 매우 긴 메서드처럼 위험이 분명한 규칙을 먼저 검토하고, 취향에 가까운 규칙은 warning 또는 info로 시작한다.
  3. 기준선을 만든다. 지금까지 있던 진단을 기준선으로 기록하면, 이후에는 새로 생긴 진단을 우선 볼 수 있다.
  4. 기준선을 자동으로 갱신하지 않는다. 새 진단이 생겼을 때 기준선을 덮어쓰면 품질 저하를 숨길 수 있다. 의도적으로 정리한 시점에만 새 기준선을 만든다.
.\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -BaselinePath .\csharprulekeeper-baseline.json -CreateBaseline
.\build\Invoke-CSharpRuleKeeper.ps1 -Solution .\MySolution.sln -BaselinePath .\csharprulekeeper-baseline.json

첫 명령은 분석이 완료된 현재 진단을 기준선 파일에 저장한다. 두 번째 명령은 기준선과 현재 결과를 비교한다. 기준선은 분석 완료 결과에서만 만들며 자동 갱신하지 않는다. 내부적으로는 규칙 ID, 파일 경로, 메시지를 조합해 같은 진단인지 비교하므로, 파일 이름 변경·같은 문맥의 중복 진단·도구 버전 변경은 보수적으로 다시 검토한다.

실행 결과와 JSON 계약

Markdown은 수정 지침이며 JSON은 자동화용 결과다. 빈 진단 목록만으로 분석 성공을 판단하지 말고 analysisCompleted, analysisStatus, executionErrors를 확인한다.

명령의 종료 코드

코드뜻다음 행동
0서식, 빌드, 분석이 끝났고 현재 정책을 통과했다.보고서를 보관할 필요가 없으면 작업을 마친다.
1분석은 끝났지만 HBCS 정책 위반이 있다.Markdown 보고서의 진단을 읽고 코드를 고친 뒤 다시 검사한다.
2서식, 빌드, 설정, 시간 초과, 보고서 생성 또는 분석 완료 확인에 실패했다.코드 규칙보다 먼저 executionErrors와 환경·빌드 오류를 해결한다.

Markdown과 JSON을 함께 보는 법

사람은 Markdown 보고서에서 파일과 수정 방향을 읽는다. 자동화 도구는 JSON의 status, analysisCompleted, diagnostics를 읽는다. 예를 들어 HBCS 진단이 0개여도 analysisCompleted=false이면 “문제가 없다”가 아니라 “검사가 끝나지 않았다”는 뜻이다.

필드의미
schemaVersion현재 보고서 형식은 1이다.
statuspassed 또는 failed다.
formatStatus / analysisStatuspassed, failed, notRun, unknown 중 하나다.

executionErrors서식·빌드·보고서·분석 완료 확인 실패를 담는다.

로컬 배포물

.\build\Publish-CSharpRuleKeeperBundle.ps1 -Version 1.1.0

명령은 Release Analyzer DLL, 실행 스크립트, HTML 안내서, README, LICENSE를 ZIP과 SHA-256 파일로 만든다. SHA-256은 압축 파일이 전달 중 바뀌지 않았는지 확인하는 긴 확인값이다. 압축을 푼 깨끗한 디렉터리에서 -Doctor와 정상·위반 샘플을 확인한다. 대상 SDK는 별도로 필요하며 GitHub·NuGet 게시이나 자격증명 사용은 자동화하지 않는다.
